# ARCUS Story Specification: ST-001

## Story Metadata
- **Story ID:** `ST-001`
- **Story Title:** Core PWA Shell, Google OAuth Authentication & Dexie.js Database Storage
- **Epic:** Foundation & Core PWA Infrastructure
- **App Name:** `step-tracker`
- **Target Local Environment:** `http://localhost:1981`
- **Primary Test Target:** Successful Google Identity OAuth token retrieval, tabbed layout shell rendering, and Dexie.js IndexedDB store initialization.

---

## User Story Statement
> **As a** user running `step-tracker` locally on port 1981,  
> **I want** to connect my Google account and have an initialized browser database within a tabbed navigation shell,  
> **So that** my authentication token is acquired safely and local storage is structurally ready to store step history.

---

## Context & Business Value
This story establishes the baseline foundation for the entire `step-tracker` PWA. By setting up the local storage engine (`Dexie.js`) and Google OAuth token workflow first, subsequent feature stories (step syncing, calendar rendering, streak calculations) can be built incrementally on top of a stable, authenticated state.

---

## Scope of Work

1. **Environment Configuration Strategy:**
    - Establish `.gitignore` to block local secrets from being committed.
    - Provide a `config.example.js` template file for repository cloners.
    - Support dynamic loading of local configuration (`config.local.js`) targeting `http://localhost:1981`.

2. **Application Shell & Tab Navigation Layout:**
    - Build a responsive HTML5 application header containing the app title (`step-tracker`), authentication status indicator, and Google Connect button.
    - Implement a 4-panel tabbed navigation UI supporting:
        - 🏠 Dashboard
        - 📅 Calendar
        - 🔍 Search Lab
        - 🗺️ Spatial Map
    - Implement client-side tab-switching logic without triggering full browser page reloads.

3. **Database Initialization (`Dexie.js`):**
    - Initialize IndexedDB persistent storage named `StepTrackerDB`.
    - Request persistent browser storage permissions (`navigator.storage.persist()`) to prevent automated browser cache eviction.
    - Define primary object stores (tables) for records and application settings.

4. **Google Identity Services Authentication:**
    - Integrate Google OAuth 2.0 Token Client workflow using the client ID loaded from configuration.
    - Request required read-only Fitness scopes:
        - `https://www.googleapis.com/auth/fitness.activity.read`
        - `https://www.googleapis.com/auth/fitness.location.read`
    - Store active access tokens securely in application state memory upon authorization.

5. **Documentation Updates:**
    - Document setup steps for `config.local.js` and local Google Cloud Console configuration in the repository documentation.

## Technical Notes & Schemas

### High-Level Storage Schema (`Dexie.js`)

| Store Name | Primary Key | Indexed Fields | Purpose |
| :--- | :--- | :--- | :--- |
| `daily_records` | `date` (`YYYY-MM-DD`) | `effective_steps`, `effective_distance_km`, `is_overridden`, `synced_at` | Historical daily fitness records and override flags |
| `settings` | `key` | None | Application runtime settings and preferences |

### Required OAuth Scopes
- Activity Read: Scope required to query `com.google.step_count.delta` and aggregated daily movement data.
- Location Read: Scope required to pull `com.google.location.sample` GPS data for spatial maps.

---

## Explicit Out of Scope
- Fetching or parsing actual step data from Google Fit APIs (covered in `ST-002`).
- Calculation of streaks, targets, or goal metrics (covered in `ST-003` / `ST-004`).
- Styling refinement, themes, or CSS animations beyond basic structural layout.
- Cloud storage backups or external API syncs (covered in `ST-012`).

## Acceptance Criteria (Definition of Done)

### Scenario 1: Local Database & Storage Initialization
- **Given** a user opens `http://localhost:1981` in a modern web browser,
- **When** the application finishes loading,
- **Then** Dexie.js initializes `StepTrackerDB` with `daily_records` and `settings` stores,
- **And** the UI reflects a database status of ready with 0 initial records.

### Scenario 2: Google Identity Service Authorization
- **Given** a valid Client ID is present in `config.local.js`,
- **When** the user clicks "Connect Google Account",
- **Then** Google's OAuth consent modal opens requesting Activity and Location permissions,
- **And** upon successful authorization, the application state stores the access token and updates the status to `Connected`.

### Scenario 3: Client-Side Navigation
- **When** the user clicks between navigation tabs (Dashboard, Calendar, Search Lab, Spatial Map),
- **Then** the UI seamlessly toggles view panels without triggering browser reloads or URL shifts.

### Scenario 4: Repository & Setup Documentation
- **Given** a new developer clones the repository,
- **When** following the project documentation,
- **Then** clear instructions are provided on how to populate `config.local.js` and register port `1981` in Google Cloud Console.
