# ARCUS Story Specification: ST-006

## Story Metadata
- **Story ID:** ST-006
- **Story Title:** Data Audit Trail, Manual Overrides and Proof Uploads
- **Epic:** Data Lineage and Integrity
- **App Name:** step-tracker
- **Target Local Environment:** http://localhost:1981
- **Primary Test Target:** Form submission for manual step/distance overrides, Base64 proof image encoding, audit metadata persistence in Dexie.js, and recalculation triggering across active streaks.

---

## User Story Statement
> **As a** user whose wearable misses treadmill workouts or runs out of battery,  
> **I want** to manually adjust my effective steps and distance for any date with a justification note and proof screenshot,  
> **So that** my true physical activity is accurately recorded without destroying raw Google Fit data lineage.

---

## Context and Business Value
Wearables and smartphones frequently miss steps during treadmill sessions, indoor walks, or when devices are charging. To maintain trust in streak and commitment metrics, users need a verified override mechanism. This story establishes an audit trail layer that preserves raw synced API data (`original_steps`) while allowing verified manual values (`effective_steps`) to take precedence in streak and target calculations.

---

## Scope of Work

1. **Manual Override UI Form:**
   - Integrate an "Edit Record / Add Override" button inside the Day Detail Drawer (built in ST-005).
   - Render an edit form with inputs for:
     - Effective Step Count (integer input)
     - Effective Distance in km (decimal input; auto-calculates from steps if left blank using stride conversion formula)
     - Justification / Audit Note (text area input)
     - Proof Image File Attachment (file picker input supporting PNG, JPG, WEBP)

2. **Image Processing and Storage Engine:**
   - Client-side file reader utility to process attached proof images.
   - Resize/compress images client-side (maximum width/height 1024px) to optimize browser storage footprint.
   - Encode processed image into a Base64 Data URL string for inline storage within the Dexie.js record.

3. **Data Lineage and Audit State Mutation:**
   - On form submit, update target date record in Dexie.js `daily_records` store:
     - Retain `original_steps` and `original_distance_km` values untouched.
     - Set `effective_steps` and `effective_distance_km` to user-submitted values.
     - Set `is_overridden` flag to `true`.
     - Construct `override` metadata object storing `note`, `proof_image_base64`, and `updated_at` ISO timestamp.
   - Stamp `synced_at` ISO timestamp.

4. **Revert to Original Synced State Utility:**
   - Provide a "Revert to Synced Data" action button for any date currently marked as overridden.
   - On confirmation, reset `effective_steps = original_steps`, `effective_distance_km = original_distance_km`, set `is_overridden = false`, and remove the `override` metadata object.

5. **Application-Wide Event and Metric Recalculation:**
   - Dispatch internal data mutation event upon override creation, update, or deletion.
   - Trigger immediate recalculation of:
     - Today's Progress Card (if today was edited)
     - Unified Active Streak and Goal-Tier Streaks (ST-004)
     - Monthly Calendar Heatmap Tile and Monthly Aggregate Header (ST-005)

6. **Documentation Updates:**
   - Update repository documentation explaining manual override workflows, data lineage preservation, image storage limits, and state reversion.

## Technical Notes and Schemas

### Updated Daily Record Schema (`Dexie.js`)

```text
{
  "date": "2026-08-08",
  "original_steps": 4200,
  "original_distance_km": 3.20,
  "effective_steps": 6500,
  "effective_distance_km": 5.00,
  "is_overridden": true,
  "override": {
    "note": "Treadmill session logged manually.",
    "proof_image_base64": "data:image/jpeg;base64,...",
    "updated_at": "2026-08-08T19:00:00.000Z"
  },
  "synced_at": "2026-08-08T10:30:00.000Z"
}

```

### Data Integrity Rules

* Raw synced values (`original_steps`, `original_distance_km`) must NEVER be overwritten or mutated by manual user edits.
* All application metrics (Streaks, Hit Rates, Calendar Heatmaps, Progress Cards) must evaluate `effective_*` fields exclusively.

## Explicit Out of Scope

* Uploading images to external cloud image servers or S3 buckets (proofs are stored locally in IndexedDB as Base64 Data URLs).
* AI or OCR text extraction from uploaded proof screenshots.
* Multi-user verification or admin approval workflows.

## Acceptance Criteria (Definition of Done)

### Scenario 1: Creating a Manual Override

* **Given** a daily record showing 4,200 synced steps (3.2 km) on a 5.0 km target date,
* **When** the user opens the Day Detail Drawer, inputs 6,500 effective steps, attaches a note and screenshot proof, and submits,
* **Then** `effective_steps` updates to 6,500, `is_overridden` becomes `true`, and Base64 proof string is saved,
* **And** `original_steps` remains 4,200,
* **And** the calendar tile updates to Met Target status with an override indicator badge.

### Scenario 2: Instant Recalculation of Active Streaks

* **Given** an override submitted for yesterday that changes a Missed day to a Met Goal day,
* **When** the submission completes,
* **Then** the Unified Active Streak engine recalculates immediately without requiring a browser refresh,
* **And** increments the active streak counter to reflect the continuous record.

### Scenario 3: Reverting an Override to Raw Synced Data

* **Given** a date currently marked `is_overridden: true`,
* **When** the user opens the Day Detail Drawer and clicks "Revert to Synced Data",
* **Then** `effective_steps` resets to match `original_steps`, `is_overridden` becomes `false`, and the override object is purged,
* **And** all streak and calendar metrics recalculate against raw synced values.

### Scenario 4: Technical Documentation Update

* **Given** completion of the data audit and override engine,
* **When** reviewing repository documentation,
* **Then** manual override mechanics, Base64 image handling, and audit lineage rules are accurately documented.
