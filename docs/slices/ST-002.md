# ARCUS Story Specification: ST-002

## Story Metadata
- **Story ID:** ST-002
- **Story Title:** Google Fit Step Fetching and Incremental Sync Engine
- **Epic:** Data Acquisition and Storage
- **App Name:** step-tracker
- **Target Local Environment:** http://localhost:1981
- **Primary Test Target:** Universal step data aggregation from Google Fit REST API across all user data sources, local midnight bucket alignment, incremental delta detection, and Dexie.js storage population.

---

## User Story Statement
> **As a** user connected with an authorized Google Account session,  
> **I want** the application to fetch my aggregated daily step counts across all connected devices and sync them into my local database,  
> **So that** my walking history is completely restored regardless of whether steps were logged by a phone, Samsung Watch, or Health Connect.

---

## Context and Business Value
Hardcoding specific device stream IDs (such as `estimated_steps`) causes data loss for users syncing steps via external wearables, Health Connect, or third-party apps. To guarantee universal data compatibility across all device setups, this story configures the step sync engine to query the root `com.google.step_count.delta` data type, constructing query buckets anchored to local midnight epoch bounds with an incremental safety buffer.

---

## Scope of Work

1. **Authentication Token Handling:**
    - Consume the short-lived OAuth `access_token` acquired during `ST-001` authentication.
    - Inject token into HTTP request headers using standard `Authorization: Bearer <access_token>` format.
    - Validate token presence prior to initiating sync calls.

2. **Local Timezone Boundary and Range Calculation:**
    - Compute aggregate time boundaries using local midnight epoch timestamps (`00:00:00.000` in local timezone) rather than UTC zero-hour.
    - Inspect IndexedDB `daily_records` store for the most recent record date before constructing API requests.
    - **First-Time Sync Rule:** If no records exist, set sync start date to local midnight 365 days prior to current timestamp.
    - **Incremental Sync Rule:** If records exist, determine `latest_record_date` and set sync start date to `latest_record_date minus 3 days` at local midnight (3-day safety buffer for delayed watch or health connect cloud pushes).
    - Set sync end date to local midnight of current day plus 24 hours.

3. **Universal API Aggregation Engine:**
    - Divide total required sync window into sequential 30-day API request chunks moving backwards from target end date.
    - Execute POST requests against Google Fitness `/dataset:aggregate` endpoint.
    - Specify `dataTypeName: "com.google.step_count.delta"` without specifying a restrictive `dataSourceId`, enabling Google Fit to aggregate step totals across all account data sources.
    - Configure aggregate buckets with a 24-hour duration (86,400,000 milliseconds) anchored to local midnight epoch bounds.

4. **Data Normalization and Processing:**
    - Convert nanosecond bucket start timestamps to ISO local date strings (`YYYY-MM-DD`).
    - Extract integer step totals from dataset values (default to 0 if dataset array is empty for a day).
    - Calculate estimated daily distance in kilometers if missing from payload using standard stride conversion (1 step = 0.000762 km).

5. **Persistence and Override Protection:**
    - Execute bulk upsert into IndexedDB `daily_records`.
    - Preserve existing records marked `is_overridden: true` by updating `original_steps` and `original_distance_km` while keeping `effective_steps` and `effective_distance_km` unchanged.
    - For standard non-overridden records, update both `original_*` and `effective_*` fields to newly fetched values.
    - Stamp `synced_at` ISO timestamp on modified records.

6. **Feedback UI:**
    - Disable sync action button during execution.
    - Display dynamic progress messages showing sync type (Full vs. Incremental) and current active date range.
    - Handle expired token errors (HTTP 401) with user re-authorization prompts.

7. **Documentation Updates:**
    - Document Bearer token usage, universal step aggregation rules, local midnight bucket math, 3-day safety buffer rationale, and override protection behavior.

## Technical Notes and Schemas

### API Endpoint & Payload Specification
- **URL:** `https://www.googleapis.com/fitness/v1/users/me/dataset:aggregate`
- **Method:** `POST`
- **Headers:**
    - `Authorization`: `Bearer <accessToken>`
    - `Content-Type`: `application/json`

```json
{
  "aggregateBy": [{
    "dataTypeName": "com.google.step_count.delta"
  }],
  "bucketByTime": { "durationMillis": 86400000 },
  "startTimeMillis": 1786213800000,
  "endTimeMillis": 1786300200000
}

```

### Sync Decision Matrix

| IndexedDB State | Max Record Date Found | Calculated Sync Start Window | Chunking Applied |
| --- | --- | --- | --- |
| Empty (0 records) | None | Local midnight 365 days ago | Yes (12 x 30-day chunks) |
| Existing Records | `2026-08-01` | Local midnight 2026-07-29 (3-day buffer) | Yes (1 chunk) |
| Up-to-Date | `Today` | Local midnight 3 days ago to Today | Yes (1 mini-chunk) |

### Override Preservation Rules

* `is_overridden == false`: Update `original_steps` AND `effective_steps`.
* `is_overridden == true`: Update `original_steps` ONLY; preserve `effective_steps` and `override` metadata object.

## Acceptance Criteria (Definition of Done)

### Scenario 1: Multi-Device Aggregated Step Sync

* **Given** a user with steps synced via phone, Samsung Watch, or Health Connect,
* **When** the step sync engine executes against Google Fit API without restricting `dataSourceId`,
* **Then** the API returns total aggregated step counts across all connected sources,
* **And** IndexedDB populates with normalized daily step entries.

### Scenario 2: Local Midnight Bucket Alignment

* **Given** a user in a non-UTC timezone (for example, IST / UTC+5:30),
* **When** query buckets are generated,
* **Then** bucket `startTimeMillis` and `endTimeMillis` correspond strictly to 00:00:00 local time,
* **And** steps taken between midnight and 05:30 AM are credited to the correct local calendar day.

### Scenario 3: Smart Incremental Delta Sync

* **Given** an existing database with records up to 10 days ago,
* **When** the user clicks "Sync Steps",
* **Then** the engine calculates a sync window starting 13 days ago (10 days + 3-day safety buffer),
* **And** executes only the necessary API requests to fill the missing gap without re-downloading the entire year.

### Scenario 4: Preservation of Manual Edits During Sync

* **Given** an existing record within the sync window marked `is_overridden: true`,
* **When** the sync engine runs,
* **Then** `original_steps` receives the newly fetched API value,
* **And** `effective_steps` retains its user-edited value.

### Scenario 5: Technical Documentation Update

* **Given** completion of the updated step sync engine,
* **When** reviewing repository documentation,
* **Then** universal step aggregation rationale, local midnight bucket conversion, and incremental sync safety windows are accurately documented.
